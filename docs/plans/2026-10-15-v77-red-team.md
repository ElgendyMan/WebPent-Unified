# خطة Red Team — محرر الإصلاح الذكي v77 (2026-10-15)

مراجعة صارمة لكل ملفات `src/webpent/remediation/` (12 وحدة) + التوصيل في
`hunt_state.py` + الاختبارات. كل مشكلة بالأسفل **مثبتة بـ repro فعلي**
(سكربت شغّل وأنتج المخرجات قبل كتابة الخطة)، وليست شكًا.

## المشاكل المثبتة (بالترتيب حسب الخطورة)

- **RT1 — P0 — KeyError على UNKNOWN في لوحة الأولويات.**
  `priority_dashboard.build_priority_dashboard` يفك `VulnClass("unknown")`
  بنجاح ثم يقرأ `_EFFORT[vuln_class]` مباشرة، و`UNKNOWN` غير موجود في
  `_EFFORT` → `KeyError`. نفس عائلة الباغ الذي صُلّح في `action_plan`
  ولم يُصلَّح هنا. النتيجة: أي تقرير hunt فيه finding بclass
  `unknown` وseverity صالح يتعطل. Repro: مُثبت (RT1).

- **RT2 — P0 — تسريب بيانات اعتماد من الـlocator.**
  `locate()` يبني `origin` من `parts.netloc` كاملًا، و`netloc` قد يحمل
  userinfo: `http://admin:hunter2@site.test/x` → origin
  `http://admin:hunter2@site.test`. عقد التخفية الصريح في docstring
  الوحدة ("credentials never reach the output") مكسور. Repro: مُثبت (RT2).

- **RT3 — P1 — الملخص التنفيذي يخترع class اسمه "None".**
  `build_executive_summary` يحوّل `vuln_class` إلى `str(...)` ويرفض فقط
  الفارغ؛ finding بلا `vuln_class` وseverity صالح → يُحتسب تحت class
  `"None"` وتصير `skipped_unclassified=0` (كذب في التغطية). كذلك
  `UNKNOWN` يُحتسب class عادي بينما كل الوحدات الأخرى تعتبره غيابًا
  صادقًا (تناقض داخلي). Repro: مُثبت (RT3).

- **RT4 — P1 — findings حاملة instances من enum تُتخطى بالخطأ.**
  `str(VulnClass.SQLI)` = `"VulnClass.SQLI"` (سلوك Python 3.12 لـ
  str-Enum)، فكل الوحدات (`get_pattern`, `pattern_for_finding`,
  `scenario_steps`, `fix_template`, الملخص، الخطة، اللوحة) تفشل في فك
  الكلاس وتحسبه skipped رغم أنه class صالح. التوصيل الحالي يمرر strings،
  لكن أي مستدعٍ يمرر الكائن كما هو من finding structure يفقد الإرشاد
  بالكامل. Repro: مُثبت (RT4).

- **RT5 — P2 — الطبقة الوقائية تعرض ids لfindings سبق تخطيها.**
  `preventive.finding_ids` في `build_action_plan` يُبنى بمطابقة نصية على
  القائمة الخام، فfinding بseverity غير صالح (سُخطي وأُحصي في
  `skipped_unclassified`) يظهر رغم ذلك في ids الطبقة الوقائية — تناقض
  بين العدّ والعرض. Repro: مُثبت (RT5).

- **RT6 — P2 — قاموس ميت وقيم مستوردة private.**
  `_EXPLOITABILITY: dict[str, float] = {}` في priority_dashboard قاموس
  فارغ ميت منذ الإنشاء. والوحدة تستورد `_EFFORT` و`_SEVERITY_WEIGHT`
  (أسماء private) من `action_plan` — تلوث حدود الوحدات.

- **RT7 — P2 — فجوات الاختبارات التي أفرطت الباغات.**
  لا اختبار: (a) dashboard مع class unknown، (b) locator مع userinfo،
  (c) ملخص مع class مفقود أو enum instance، (d) ids الطبقة الوقائية ضد
  findings مُخطاة. الباغات الخمسة فوق كلها نجت من 36 اختبارًا.

- **RT8 — P3 — README قديم بخمس إصدارات.**
  سطر الحالة في README يقول v60 و865 اختبارًا؛ الحقيقة v77 و2281.

## مبدأ الإصلاح الموحد

منطق فك الحقول (severity + vuln_class) مكرر بثلاث صيغ متضاربة في
`action_plan` و`executive_summary` و`priority_dashboard`. يُوحَّد في
وحدة داخلية واحدة `remediation/_fields.py`:
`as_vuln_class(value) -> VulnClass | None` (تقبل str/enum instance،
ترفض garbage، وتعيد None لUNKNOWN) و`as_severity(value)` و
`EFFORT` / `SEVERITY_WEIGHT` كأسماء عامة. كل الوحدات الأربع تستخدمها.
