## Phase 3-4 — Real Contract Trace + Causal Feedback Bridge

### Task 3.1: Implement WorldModel + ObservationStore

**New files:**
- `src/webpent/llm_researcher/world_model.py`
- `src/webpent/llm_researcher/observation_store.py`

**WorldModel responsibilities:**
- Stores observations keyed by `(method, path, headers_fingerprint)`
- Each observation has deterministic `content_hash` (SHA-256)
- `update(observation)` → returns `{added: bool, hash: str}`
- `get_causal_inputs()` → returns list of observations for CausalGuard
- `get_hashes()` → returns dict of hashes for audit trail

**ObservationStore:** Simple bounded store (max 100 observations) with hash-based deduplication.

### Task 3.2: Implement CausalFeedbackBridge

**New file:** `src/webpent/llm_researcher/causal_feedback_bridge.py`

**Interface:**
```python
class CausalFeedbackBridge:
    def __init__(self, world_model, tool_boundary, researcher):
        self.world_model = world_model
        self.tool_boundary = tool_boundary
        self.researcher = researcher

    def run_research_loop(self, initial_observations, max_loops=3):
        """
        1. Baseline deterministic evaluation
        2. If INCONCLUSIVE or FN-pattern:
           a. LLM generates hypotheses from current world model
           b. Top hypothesis → select experiment
           c. Execute tool → get new observation
           d. Add to world model (with content hash)
           e. Re-run deterministic evaluation on updated causal inputs
        3. Return: final verdict, trajectory, hashes
        """
```

**Critical invariants:**
- Bridge NEVER writes verdicts
- Bridge NEVER modifies causal rules/thresholds
- Bridge ONLY adds observations
- Every new observation has deterministic content hash
- Final verdict from CausalGuard only

## Phase 5 — Re-evaluation After LLM Exploration

### Task 5.1: Fix the dead path in differential runner

**File to create:** `goed_v1_8_3/differential_runner.py`

**Required loop per case:**
```
initial_observations → baseline_eval (CausalGuard)
if baseline_eval.verdict in (INCONCLUSIVE, CLEAN) and is_vulnerable_case:
    run research loop (max 3 iterations)
    if new observations added:
        re_eval = CausalGuard on updated world model
        final_verdict = re_eval.verdict
    else:
        final_verdict = baseline_eval.verdict
else:
    final_verdict = baseline_eval.verdict
```

**Recoverable case definition:**
- LLM OFF baseline = FN (vulnerable but missed)
- LLM ON → additional experiment → new observation → CausalGuard = CONFIRMED

**NOT recoverable:** hypothesis alone, LLM confidence alone, anything not causally confirmed.

## Phase 6-8 — Differential Benchmark v2 (90 cases, blind, no leakage)

### Task 6.1: Build DifferentialBenchmark-v2 target

**Files to create:**
- `benchmarks/differential_v2/differential_target_v2.py`
- `benchmarks/differential_v2/manifest.json`
- `benchmarks/differential_v2/ground_truth.json` (INDEPENDENT evaluator only)

**Design principles:**
- **NO** vulnerability names in responses
- **NO** mechanism labels ("workflow", "ownership", "multi-step")
- **NO** internal flags ("ownership_check_bypassed")
- **NO** difficulty indicators
- **NO** evaluator hints
- Behavior reveals itself ONLY through: HTTP status codes, headers, body content, timing, state transitions, resource relationships

**Structure:**
- **Family A (30 easy/deterministic):** Clear ownership/auth patterns in headers. CausalGuard catches.
- **Family B (30 reasoning-heavy):** Vulnerability visible only through MULTIPLE observations.
  - State transition: POST to /api/items/{id}/approve changes GET behavior on /api/items/{id}
  - Hidden prerequisite: /api/workflow/step1 must be called before /api/workflow/step2 grants access
  - Cross-resource: /api/groups/{gid}/members affects /api/resources/{rid} access
  - Multi-step workflow: 3 endpoints must be called in sequence
  - Delayed side effect: POST to /api/write makes GET /api/other vulnerable
  - Indirect authorization: User → Role → Permission → Resource chain
  - Equivalent representation mismatch: /api/item/{id} vs /api/items?id={id} have different auth
  - Role transition: POST /api/role/switch changes subsequent GET behavior
  - Tenant boundary interaction: Cross-tenant group membership
  - Nested business process: Order → Invoice → Payment chain
  - Invariant violation: Counter exceeds limit but access still granted
- **Family C (30 novel composition):** Combinations of B patterns never seen before.

**Implementation:** Stateful HTTP server using `socketserver.ThreadingMixIn` or simple in-memory dict for state.
Each case gets its own isolated state namespace.

**Response bodies:** Generic JSON only. No mechanism keywords. Use neutral field names: `status`, `data`, `id`, `ref`, `count`, `flag`, `meta`.

### Task 7.1: Audit for semantic leakage

**Script:** `goed_v1_8_3/leakage_audit.py`

Scans every response body, header, route, parameter, cookie, identifier, metadata for:
- Vulnerability names: "idor", "bac", "vulnerability", "exploit", "bypass"
- Security outcomes: "granted", "denied", "authorized" in body (allowed in headers only for actual auth)
- Mechanism labels: "workflow", "ownership", "multi-step", "prerequisite", "stateful"
- Internal flags: "check_bypassed", "vuln", "weak", "insecure"
- Evaluator clues: "difficulty", "family", "case_type", "expected"

Any finding → FAIL benchmark.

### Task 8.1: Verify ≥30 cases require multiple observations

For each reasoning/novel case, verify that a SINGLE static observation produces INCONCLUSIVE from CausalGuard,
but MULTIPLE observations (after state transitions) produce CONFIRMED.
